# 开发工作流 — Workflow

MyAnimeDock 功能开发/修 bug 的标准流程。

## 核心原则

- **唯一硬性步骤：需求对齐**。其余（通读/细读/实现方案/分 lane）由 agent 判断，不拆阶段给用户看
- **约束文件驱动验证**：`docs/dev/frontend.md` / `docs/dev/backend.md` 定义各侧规则和验证命令
- **不留死代码**：旧代码/旧字段/旧路由直接删，默认不做兜底

## 流程图

```
输入分类 ─→ 需求对齐 ─→ 实现(agent内部) ─→ 验证 ─→ 报告
  │            │            │              │        │
  └─ 走哪条路   └─ 需求表     └─ 通读/细读    └─ 约束文件 └─ 一句话
  └─ 用户确认
```

---

## 输入分类

**入口条件**：接到一个需求/bug/想法。

| 输入 | 走哪条路 |
|------|---------|
| 功能需求（明确或模糊） | **主流程** |
| Bug 报告 | **路径 A：Bug 修复** |
| "怎么实现 X"/"哪个方案好" | **路径 B：设计讨论** |
| 纯文案/样式微调（≤20 行、无逻辑变更） | **路径 C：微调快路径** |

### Checklist

- [ ] 输入类型判断（见上表）
- [ ] 这个需求在项目范围内吗？（不在范围则履行拒绝协议：说明理由 → 给出范围内的替代方向 → 问用户是否仍要做）
- [ ] 如果发现比用户说的更好的方案（更简单/更快/更稳），先说明差异+理由，等用户确认再继续

## 主流程（功能需求）

```
需求对齐(需求确认表 + question 确认) → 实现(agent 内部) → 验证 → 报告
```

### 需求对齐（唯一硬性步骤）

**入口条件**：所有功能需求必经此步。修明确 bug 不适用。

#### 核心原则：禁默认通过

> **在用户使用 `question` 工具明确确认"可以开始"之前，不得进入实现。**
>
> 以下情况均视为**未确认**，不得继续：
> - 用户沉默未回复
> - 用户说"随便"/"你决定"/"你觉得行就做"/"按你说的来"
> - agent 自认为"需求够清楚了，不用问了"
> - 只问了 1-2 个问题就默认同意推进

#### 需求确认表

| 项目 | 内容 |
|------|------|
| 做什么 | 功能行为描述，贴近实际使用场景 |
| 收益 | 解决什么问题、值不值得做 |
| 代价 | 可选：主要成本/风险 |
| Fallback（兜底） | **默认不做**。旧代码/旧字段/向后兼容直接删，死代码是 bug 源。仅当主路径走不通且用户明确要求时才做 |
| 你的建议/评价 | agent 对需求本身的独立看法：值不值得做、有无更简做法、风险顾虑 |
| 边界情况 | 关键边界场景及处理方式 |

#### Checklist

- [ ] **加载 `skill("req-implement-test")` 出需求确认表**
- [ ] 需求表必须覆盖以上**全部维度**，缺一不可
- [ ] **实现细节不上表**：数据来源、影响范围/文件列表、行为细节、验收标准、前置依赖由 agent 内部把握，不逐条展示给用户（验收标准在测试阶段自行对照）
- [ ] **使用 `question` 工具做最终确认**：出"没问题，开始实现" / "需要修改" 选项。不可用陈述句替代（如"那我们开始吧"）
- [ ] 用户选"需要修改" → 更新表格 → **再次用 `question` 确认**，循环直到选"开始实现"
- [ ] **模糊回复处理**：用户说"你决定"/"你觉得行就做" → agent 把当前推荐打包成 proposal，用 `question` 工具提交二选一，获得明确确认后才算通过
- [ ] 变更控制：如果实现中途发现需求需要偏离原表，先问用户再改
- [ ] 确认通过后才进入实现，**缺任何一步不得跳过**

#### 不适用

- bug 复现路径清晰（不涉及设计方案选择）
- 纯文案/样式微调（不涉及功能逻辑变更）

**示例**：
> 需求："加个批量操作功能"
> → 需求对齐必走 req-implement-test
>
> | 项目 | 内容 |
> |------|------|
> | 做什么 | 列表页支持勾选多部动漫后批量操作 |
> | 收益 | 重复操作从逐条点击变成一次完成 |
> | 代价 | 多选状态管理（可选） |
> | Fallback | 默认不做；含无法批量处理的数据时提示并跳过 |
> | 你的建议/评价 | 建议先只做批量标记观看，批量删除风险高 |
> | 边界情况 | 全选/空选、跨页勾选、部分失败 |
>
> 用户选 → 进入实现

### 实现（agent 内部）

**入口条件**：需求已确认。

通读、细读、实现方案、分 lane 由 agent 自行判断，不拆阶段给用户看。

#### 硬闸门：先读约束文件

**实现前必须读对应约束文件，没读不算开始：**
- 前端改动 → 读 `docs/dev/frontend.md`
- 后端改动 → 读 `docs/dev/backend.md`
- 前后端都改 → 两套都读

> 验证命令是强制执行器：`check:frontend` / `typecheck`+`server test` 跑不过 = 不算完成。

#### Checklist

- [ ] **先读约束文件**（见上，硬闸门）
- [ ] 多文件改动 → 分 lane 并行交给 @fixer
- [ ] 修改前读一遍改到的每个文件的现有逻辑，确认不会破坏已有功能
- [ ] 变更控制：实现中发现偏离需求 → 更新需求表重新确认

---

### 验证

按改动范围跑对应验证（由约束文件决定）：

| 改动范围 | 约束文件 | 验证命令 |
|---------|---------|---------|
| 仅 `frontend/src/**` | `docs/dev/frontend.md` | `npm run check:frontend` |
| 仅 `server/**` | `docs/dev/backend.md` | `npm run typecheck` + `cd server && npm test` |
| 前后端都改 | 两套 | 两套验证都跑 |

---

### 报告

- [ ] 一句话总结（改了什么 + 验证结果）
- [ ] **文档影响映射** — 根据改动的文件，逐项检查对应文档是否需要更新：

  | 改了什么 | 需要检查的文档 |
  |----------|---------------|
  | `server/routes/*.ts`（新增/改路由） | `docs/data-flow.md` 枢纽表 + `docs/data-flow/` 对应子文件 |
  | `server/db.ts`（持久化逻辑） | `docs/data-flow/save-taxonomy.md` |
  | `server/scrapers/*.ts`（爬虫/匹配） | `docs/data-flow/import-metadata.md` + `docs/code-explorer.md` |
  | `server/scanner.ts`（扫描逻辑） | `docs/data-flow/scan-discovery.md` + `docs/code-explorer.md` |
  | `frontend/src/components/*.svelte` + `frontend/src/views/*.svelte` + `frontend/src/lib/*.js`（前端逻辑） | `docs/dev/frontend.md`（组件表/检查清单） |
  | `frontend/src/css/*.css`（样式） | `docs/dev/frontend.md` 必读章节、token/组件表 |
  | 新的边缘条件/隐式逻辑 | `docs/data-flow/gotchas.md` |
  | `docs/dev/*.md`（规范本身） | 无需映射（改了啥自己清楚） |

  > 操作方式：找到映射表中的对应行 → 打开对应文档 → grep 关键路径和函数名 → 确认内容未过时 → 必要时更新。

- [ ] **发现隐式业务逻辑/实现细节**（播放决策规则、ep.progress 单位、auto-complete 触发条件等） → 写入 `docs/data-flow/` 对应子文件或 `gotchas.md`
- [ ] **触发条件**：满足以下任一才跑 `skill("code-reviewer")`：
  - 改动涉及数据持久化/权限/安全性
  - 改动跨 3+ 文件或 100+ 行
  - 用户明确要求审查
- [ ] 外部输入改动 → `skill("security-review")`
- [ ] 回归测试（与改动范围匹配的路径，选相关项手动验证）
- [ ] commit（用户允许时）

## 替代路径

### 路径 A：Bug 修复

用户反馈 bug 时，**不要直接开始修**。按此协议响应：

#### 1. 事故报告

- [ ] 问清结构：做了什么操作 → 实际看到什么 → 期望看到什么 → 是否每次必现
- [ ] 给用户一个"明白了，正在定位"确认，不要 silent 开始修

#### 2. 分层诊断（5 秒排除法）

**不要先读代码。先确认哪个层出了问题：**

| 现象 | 嫌疑层 | 验证方法 |
|------|--------|----------|
| 页面渲染/交互不对 | 前端 | F12 → `__debug.toggle()` → 重试 → 看 console 和 DOM |
| 数据内容不对 | 后端 API | 看 `npm run dev:server:watch` 输出或直接请求对应 API |
| 重启后丢失 | 持久化 | `cd server && node --test __tests__/db.test.js` |
| 外部数据/匹配不对 | 爬虫/匹配 | `cd server && node --test __tests__/scrapers.test.js` |
| 扫描文件不对 | Scanner | `cd server && node --test __tests__/scanner.test.js` |

**原则**：5 秒确定嫌疑层，剩下 95% 的代码直接不看。

#### 3. 假设驱动排查

**禁止改生产代码。只加探针，不加改动。**

每轮循环只做三件事：

1. **写假设** — 一句话：「我怀疑 `XX:YY` 在 `ZZ` 条件下得到了错误输入」
2. **加一处探针** — 在假设指向的位置加 `console.log` / `__debug.log`
3. **跑一次验证** — 复现操作，看探针输出

确认 → 进入第 4 步。否定 → 删掉探针 → 写新假设 → 新位置加探针 → 跑。

> ⚠️ 一条探针只验证一个假设。不要同时加多处日志"看看有什么"。
> 移位置时删掉旧探针（调试日志不积累，修完也无需清理）。

| 层 | 探针方式 |
|----|----------|
| 前端 | `__debug.log('TAG', data)` / `__debug.snapshot('描述')` |
| 后端路由 | handler 入口加 `console.log('DEBUG:', {body, query, params})` |
| DB 读写 | save/load 前后加 `logger.info('DB:', data)` |
| 播放路径 | mpv 调用前加 `console.log('DEBUG: path', path)` |

#### 4. 根因声明 + 修复

**改任何代码之前，必须先能写出根因声明：**

> 根因：`xxx` 中 `yyy` 因为 `zzz` 导致 `www`。
> 示例：根因：`Library.svelte` 中渲染卡片处（如 `{#each}` 循环里的 `AnimeCard`）在 `data.episodes` 为 null 时没有 fallback，导致渲染出 `undefined`。

写不出一句根因 → **回到第 3 步**，禁止进入修复。

- [ ] 写出根因声明（向用户说明时也用这一句）
- [ ] 用户确认后再改
- [ ] 后端 bug → 先写复现测试再改
- [ ] 最小改动：不改无关文件、不新增不需要的模块、不改同名但不同功能的代码
- [ ] 修复后确保无残留调试日志

#### 5. 验证 + 报告

- [ ] 验证修复：重走第 1 步的复现路径，确认问题不再出现
- [ ] 跑对应测试全绿（后端必跑，前端手动验证）
- [ ] 回归检查：选相关项快速验证不破坏已有功能（server 启动、库加载、播放、同步）
- [ ] 报告：一句话（根因 + 修改文件 + 测试结果）

### 路径 B：设计讨论

当用户问"怎么做"、"哪个方案好"、"如何实现 X"等开放问题时，**不要直接给一个答案**。

#### 约束

1. **先探索再回答** — 不凭记忆直接给方案。读相关代码/文档确认现有模式
2. **带选项** — 给出 ≥2 个方案，每个说明 tradeoffs：
   - 复杂度（实现难度、新增多少代码）
   - 维护成本（后续改的时候会不会容易出错）
   - 对现有架构的影响
3. **推荐** — 在选项中给出推荐及理由
4. **问清楚再做** — 如果描述不明确，先用 `question` 工具问清楚再给方案
5. **不在讨论阶段写代码** — 讨论就是讨论，等用户选了方向后才进入实现

### 路径 C：微调快路径

适用于**纯文案/样式微调**：≤20 行、不涉及逻辑变更、不改数据模型。例如：
- 改 `frontend/src/lib/i18n-zh.js` 里的文案值
- 静态 HTML 的 `data-i18n` / `data-i18n-attr` 文本
- 已有 CSS 的 token 值微调（不改结构）

**豁免**：需求对齐、code-reviewer、report.md 总结。

**必须做**：
- [ ] 改动范围一句话说清（改哪个文件哪个值 → 改成什么）
- [ ] 验证：`npm run check:frontend`（node --check + check:css + build:frontend 一键）
- [ ] 报告：一句话（改了什么 + 验证结果）

> ⚠️ 判定标准是"无逻辑变更"。只要动了 JS 逻辑、加了新 key、改了路由/数据 → 回到主流程或路径 A/B。
