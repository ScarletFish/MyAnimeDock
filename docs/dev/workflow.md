# 开发工作流 — Workflow

MyAnimeDock 功能开发/修 bug 的标准流程。**禁止跳过阶段直接写代码**。

## 流程图

```
方向判断 ─→ 前置研究 ─→ 需求确认 ─→ 实现 ─→ 测试 ─→ 审查+报告
  │             │            │          │        │          │
  └─ 该不该做?   └─ 读代码    └─ 需求表   └─ 按规范 └─ 跑测试  └─ 审查 + 更新文档
  └─ 哪个方案?   └─ 读文档    └─ 用户确认  └─ 分 lane └─ 调绿   └─ report.md
```

---

## 替代路径

不是所有输入都走 6 阶段主流程。根据输入类型走对应路径。

### 路径 A：Bug 修复

用户反馈 bug 时，**不要直接开始修**。按此协议响应：

#### 1. 事故报告

- [ ] 问清结构：做了什么操作 → 实际看到什么 → 期望看到什么 → 是否每次必现
- [ ] 给用户一个"明白了，正在定位"确认，不要 silent 开始修

#### 2. 分层诊断（5 秒排除法）

**不要先读代码。先确认哪个层出了问题：**

| 现象 | 嫌疑层 | 验证方法 |
|------|--------|----------|
| 页面渲染/交互不对 | 前端 | F12 → `__debug.toggle()` → 重试 → 看 console 和 DOM |
| 数据内容不对 | 后端 API | 看 `npm run dev:server:watch` 输出或直接请求对应 API |
| 重启后丢失 | 持久化 | `cd server && node --test __tests__/db.test.js` |
| 外部数据/匹配不对 | 爬虫/匹配 | `cd server && node --test __tests__/scrapers.test.js` |
| 扫描文件不对 | Scanner | `cd server && node --test __tests__/scanner.test.js` |

**原则**：5 秒确定嫌疑层，剩下 95% 的代码直接不看。

#### 3. 假设驱动排查

**禁止改生产代码。只加探针，不加改动。**

每轮循环只做三件事：

1. **写假设** — 一句话：「我怀疑 `XX:YY` 在 `ZZ` 条件下得到了错误输入」
2. **加一处探针** — 在假设指向的位置加 `console.log` / `__debug.log`
3. **跑一次验证** — 复现操作，看探针输出

确认 → 进入第 4 步。否定 → 删掉探针 → 写新假设 → 新位置加探针 → 跑。

> ⚠️ 一条探针只验证一个假设。不要同时加多处日志"看看有什么"。
> 移位置时删掉旧探针（调试日志不积累，修完也无需清理）。

| 层 | 探针方式 |
|----|----------|
| 前端 | `__debug.log('TAG', data)` / `__debug.snapshot('描述')` |
| 后端路由 | handler 入口加 `console.log('DEBUG:', {body, query, params})` |
| DB 读写 | save/load 前后加 `logger.info('DB:', data)` |
| 播放路径 | mpv 调用前加 `console.log('DEBUG: path', path)` |

#### 4. 根因声明 + 修复

**改任何代码之前，必须先能写出根因声明：**

> 根因：`xxx` 中 `yyy` 因为 `zzz` 导致 `www`。
> 示例：根因：`library.js:120` 的 `renderCard()` 在 `data.episodes` 为 null 时没有 fallback，导致 `card.innerHTML` 拼接了 `undefined`。

写不出一句根因 → **回到第 3 步**，禁止进入修复。

- [ ] 写出根因声明（向用户说明时也用这一句）
- [ ] 用户确认后再改
- [ ] 后端 bug → 先写复现测试再改
- [ ] 最小改动：不改无关文件、不新增不需要的模块、不改同名但不同功能的代码
- [ ] 修复后确保无残留调试日志

#### 5. 验证 + 报告

- [ ] 验证修复：重走第 1 步的复现路径，确认问题不再出现
- [ ] 跑对应测试全绿（后端必跑，前端手动验证）
- [ ] 回归检查：选相关项快速验证不破坏已有功能（server 启动、库加载、播放、同步）
- [ ] 报告：一句话（根因 + 修改文件 + 测试结果）

### 路径 B：设计讨论

当用户问"怎么做"、"哪个方案好"、"如何实现 X"等开放问题时，**不要直接给一个答案**。

#### 约束

1. **先探索再回答** — 不凭记忆直接给方案。读相关代码/文档确认现有模式
2. **带选项** — 给出 ≥2 个方案，每个说明 tradeoffs：
   - 复杂度（实现难度、新增多少代码）
   - 维护成本（后续改的时候会不会容易出错）
   - 对现有架构的影响
3. **推荐** — 在选项中给出推荐及理由
4. **问清楚再做** — 如果描述不明确，先用 `question` 工具问清楚再给方案
5. **不在讨论阶段写代码** — 讨论就是讨论，等用户选了方向后才进入实现

### 路径 C：Escalation（需要人工介入）

当 agent 遇到自己无法完成的事，**不能 silent 继续**或瞎猜。适用场景：
- 缺少 API key / 配置
- 环境问题（ffmpeg PATH、Node.js 版本）
- 需要用户提供路径、文件、密码等
- 需要用户手动操作（装软件、改系统设置）
- 任何你不确定但对结果有影响的事

#### 协议

1. **识别** — 确认这是"要人动手"的事，不是 agent 能代码解决的
2. **停** — 立即停下，不出代码、不出猜测、不绕过
3. **说清楚** — 需要用户做什么、为什么需要、不做的话什么后果
4. **给步骤** — 具体可执行的步骤（"在 `server/config.json` 里填上你的 Bangumi Client ID"），不要笼统的"需要配认证"
5. **等** — 用 `question` 工具问，或用 `wait_for_user` 让用户操作完后回来通知你。不等就不继续

**只属于"提醒"不算 Escalation**（比如"这是 dev 模式，生产构建不同"）——那直接说就行，不需要停。

### 路径 D：微调快路径

适用于**纯文案/样式微调**：≤20 行、不涉及逻辑变更、不改数据模型。例如：
- 改 `frontend/src/js/i18n-zh.js` 里的文案值
- 静态 HTML 的 `data-i18n` / `data-i18n-attr` 文本
- 已有 CSS 的 token 值微调（不改结构）

**豁免**：阶段 2 需求确认表、阶段 5 code-reviewer、report.md 总结。

**必须做**：
- [ ] 改动范围一句话说清（改哪个文件哪个值 → 改成什么）
- [ ] 验证：`npm run check:frontend`（node --check + check:css + build:frontend 一键）
- [ ] 报告：一句话（改了什么 + 验证结果）

> ⚠️ 判定标准是"无逻辑变更"。只要动了 JS 逻辑、加了新 key、改了路由/数据 → 回到 6 阶段主流程或路径 A/B。

## 阶段 0：方向判断

**入口条件**：接到一个需求/bug/想法。

### 先判断输入类型

| 输入 | 走哪条路 |
|------|---------|
| 功能需求（明确或模糊） | **6 阶段主流程，阶段 2 需求确认必走** |
| Bug 报告 | **路径 A：Bug 修复** |
| "怎么实现 X"/"哪个方案好" | **路径 B：设计讨论** |
| 纯文案/样式微调（≤20 行、无逻辑变更） | **路径 D：微调快路径** |
| 需要人工操作/配置 | **路径 C：Escalation** |

### Checklist

- [ ] 输入类型判断（见上表）
- [ ] 这个需求在项目范围内吗？（不在范围则履行拒绝协议：说明理由 → 给出范围内的替代方向 → 问用户是否仍要做）
- [ ] 如果发现比用户说的更好的方案（更简单/更快/更稳），先说明差异+理由，等用户确认再继续

**示例**：
> 需求："希望首页列表能记住滚动位置"
> 判断：已有 `libraryScrollPositions` Map + `restoreLibraryScroll()`
> → 看具体丢失场景 → 阶段 1 读代码即可，不需要阶段 2 需求表

## 阶段 1：前置研究

**入口条件**：方向确定，需要理解现有代码/数据流/架构。

### Checklist

- [ ] 读 `docs/data-flow.md`（按改动范围选子文件，见枢纽表格）
- [ ] 读 `docs/code-explorer.md`（跨模块改动时读）
- [ ] 小改动（单文件 ≤20 行、纯逻辑、不涉及数据模型）→ 直接读相关文件代码
- [ ] 新功能/大改 → `skill("code-architect")` 出设计蓝图
- [ ] 外部库不确定 → `@librarian` 查文档
- [ ] 读 `CHANGELOG.md`（如有）看看最近的修改
- [ ] 列出要改的文件列表（含文件名+改动方向），确认没有遗漏

### 输出

- 改动文件列表
- 关键数据流路径
- 风险点（如有）

**示例**：
> 目标：添加筛选栏记住最后选中的筛选条件
> 读：`docs/data-flow.md` → Config 字段
> 读：`library.js` → `createFilterBar()` + `renderLibrary()`
> 读：`state.js` → UIState
> 结论：加字段到 UI state + localStorage，2 个文件

## 阶段 2：需求确认

**入口条件**：所有功能需求必经此阶段。修明确 bug 不适用。

### 核心原则：禁默认通过

> **在用户使用 `question` 工具明确确认"可以开始"之前，不得进入阶段 3（实现）。**
>
> 以下情况均视为**未确认**，不得继续：
> - 用户沉默未回复
> - 用户说"随便"/"你决定"/"你觉得行就做"/"按你说的来"
> - agent 自认为"需求够清楚了，不用问了"
> - 只问了 1-2 个问题就默认同意推进

### Checklist

- [ ] **加载 `skill("req-implement-test")` 出需求确认表**
- [ ] 需求表必须覆盖以下**全部维度**，缺一不可：
  - 功能描述（做什么 + 核心价值）
  - 数据来源（API/本地/外部）
  - 边界情况（≥3 项）
  - 验收标准（≥3 条可测试条件）
  - 影响范围（文件列表 + 模块）
  - 非目标（明确不做什么）
- [ ] **使用 `question` 工具做最终确认**：出"没问题，开始实现" / "需要修改" 选项。不可用陈述句替代（如"那我们开始吧"）。
- [ ] 用户选"需要修改" → 更新表格 → **再次用 `question` 确认**，循环直到选"开始实现"
- [ ] **模糊回复处理**：用户说"你决定"/"你觉得行就做" → agent 把当前推荐打包成 proposal，用 `question` 工具提交二选一，获得明确确认后才算通过
- [ ] 变更控制：如果实现中途发现需求需要偏离原表，先问用户再改
- [ ] 确认通过后才进入阶段 3，**缺任何一步不得跳过**

### 不适用

- bug 复现路径清晰（不涉及设计方案选择）
- 纯文案/样式微调（不涉及功能逻辑变更）

**示例**：
> 需求："加个批量操作功能"
> → 阶段 2 必走 req-implement-test
> 需求表列：哪些操作（批量删除？批量标记观看？批量编辑元数据？）
> 用户选 → 进入阶段 3

## 阶段 3：实现

**入口条件**：需求清晰、代码理解充分、改动范围确认。

### Checklist

- [ ] 遵守以下 Key Patterns（至少过一遍不遗漏）：
  - API 调用 → `API.get/post/del`
  - 用户数据 → `escHtml()` / `escAttr()` 包裹
  - 动画 → GSAP，非 CSS transition/Web API
  - 持久化 → 只写实际修改的表（`db.saveLibrary()` 等，不调全量 `saveData()`）
- [ ] CSS 缩放必须用 `--scale` calc，禁止 `zoom`
- [ ] 新增 CSS 遵循"先找后写"三步协议（见 `docs/dev/frontend.md` 必读章节）：
  - ① 现有组件库有没有？→ 有则用，不写新 class
  - ② 没有组件，有无 token 可用？→ 用 `var(--xxx)` 组合
  - ③ 都不够且有必要抽象？→ 放对文件，不新建 .css 文件
  - 所有间距/颜色/圆角/字号必须用 `var(--xxx)` token，**禁止写死值**
- [ ] CSS 合规自动检查：`npm run check:frontend`（内含 check:css --strict），确认无违规
- [ ] 多文件改动 → 分 lane 并行交给 @fixer
- [ ] 数据相关改动 → 写细粒度 save（只改实际修改的表，不调全量 saveData）
- [ ] 外部输入 → 用 escHtml/escAttr 防护 XSS
- [ ] 修改前读一遍改到的每个文件的现有逻辑，确认不会破坏已有功能

**示例**：
> 修改批量标记观看功能
> 1. 路由层：`routes/mylist.js` 新增 `/api/mylist/batch-watch`
> 2. DB 层：`db.js` 新增 `batchUpdateEpisodesWatched()` 批量写 SQLite
> 3. 前端：`mylist.js` 加按钮 + API 调用
> 4. 前端改 → CSS 遵循"先找后写"三步协议，完成后跑 `npm run check:frontend`

## 阶段 4：测试

**入口条件**：代码已修改。

### Checklist

- [ ] 数据相关改动 → `cd server && npm test`（或窄范围 `node --test __tests__/xx.test.js`）
- [ ] 修 bug → 先写复现测试再改代码
- [ ] 新增持久化功能 → 测试必须覆盖"修改 → loadData() 重载 → 验证"路径
- [ ] 新增 scanner 类型 → 按 scanner.test.js 模式（纯函数 + 文件系统集成）
- [ ] 如果改动完全不涉及数据层（纯 UI 文案/样式），可以不跑测试
- [ ] 凡有 CSS 新增/修改 → `npm run check:frontend`（内含 check:css --strict），确认 token 合规无违规
- [ ] 测试全绿后进入阶段 5

### 运行策略

| 范围 | 命令 | 耗时 |
|------|------|------|
| 匹配逻辑改动 | `node --test __tests__/scrapers.test.js` | ~135ms |
| scanner 改动 | `node --test __tests__/scanner.test.js` | 秒级 |
| 数据持久化改动 | `node --test __tests__/db.test.js` | 秒级 |
| 全量 | `cd server && npm test` | ~30s |

---

## 阶段 5：审查 + 报告

**入口条件**：测试全绿。

### Checklist

- [ ] **触发条件**：满足以下任一才跑 `skill("code-reviewer")`：
  - 改动涉及数据持久化/权限/安全性
  - 改动跨 3+ 文件或 100+ 行
  - 用户明确要求审查
  - 其他情况直接进下一项
- [ ] 外部输入改动 → `skill("security-review")`
- [ ] **文档影响映射** — 根据改动的文件，逐项检查对应文档是否需要更新：

  | 改了什么 | 需要检查的文档 |
  |----------|---------------|
  | `server/routes/*.js`（新增/改路由） | `docs/data-flow.md` 枢纽表 + `docs/data-flow/` 对应子文件 |
  | `server/lib/db.js`（持久化逻辑） | `docs/data-flow/save-taxonomy.md` |
  | `server/scrapers/*.js`（爬虫/匹配） | `docs/data-flow/import-metadata.md` + `docs/code-explorer.md` |
  | `server/scanner.js`（扫描逻辑） | `docs/data-flow/scan-discovery.md` + `docs/code-explorer.md` |
  | `frontend/src/js/*.js`（前端逻辑） | `docs/dev/frontend.md`（组件表/检查清单） |
  | `frontend/src/css/*.css`（样式） | `docs/dev/frontend.md` 必读章节、token/组件表 |
  | 新的边缘条件/隐式逻辑 | `docs/data-flow/gotchas.md` |
  | `docs/dev/*.md`（规范本身） | 无需映射（改了啥自己清楚） |

  > 操作方式：找到映射表中的对应行 → 打开对应文档 → grep 关键路径和函数名 → 确认内容未过时 → 必要时更新。

- [ ] **发现隐式业务逻辑/实现细节**（播放决策规则、ep.progress 单位、auto-complete 触发条件等） → 写入 `docs/data-flow/` 对应子文件或 `gotchas.md`
- [ ] 填写 `docs/dev/report.md` 格式的变更总结（改动文件数、行数、测试结果、未解决的问题）
- [ ] 回归测试（与改动范围匹配的路径，选相关项手动验证）：
  - 后端改动 → `npm run dev:server:watch` 启动无报错 + 改的 API 响应正确
  - 前端改动 → 对应页面渲染正常 + 交互正确
  - 数据改动 → 重启后数据不丢失（或已验证 loadData 重载正确）
- [ ] commit（用户允许时）

**示例 report 摘要**：
```
## 变更总结
- 文件：5 个（2 backend + 3 frontend）
- 新增：+127 行，删除：-34 行
- 测试：222/222 pass
- 文档更新：docs/data-flow.md 新增 /api/mylist/batch-watch
- 待解决：批量操作 UI 的 loading indicator 下次迭代优化
```
